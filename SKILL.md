# 3D Web Game Pipeline (Blender -> Godot -> Browser)

Use this skill when asked to build, extend, debug or host a real 3D game that runs in a
browser, especially when Blender and/or Godot are the requested tools, and when the work
must be *verified running*, not just written.

## Non-negotiable rules

1. **Asset geometry is generated by scripts, never by hand.** Every asset family gets its
   own headless Blender script so it is deterministic, re-runnable and diffable.
2. **Publish every build to the viewer.** Models (`.glb`) and renders (`.png`) must land in
   the agent's 3D viewer panel after *every* build, so the operator can watch progress.
3. **Verify with numbers, not vibes.** Extend a single `--verify` self-test that asserts
   distances, health deltas, ammo, alignment dots and writes framebuffer PNGs. A feature is
   only "done" when the self-test prints evidence.
4. **Never leave a broken server.** Rebuild exports into a staging dir, then swap; keep the
   host process alive; tell the operator the exact URL.
5. **Two-failure pivot.** If the same approach fails twice, stop and change technique
   (the war stories in `reference/` exist precisely because most first approaches fail).

## Stage 0 - recon before writing anything

```bash
blender --version; godot --version            # 4.x required for the Web export
ls ~/.local/share/godot/export_templates/*/    # web_release.zip must exist
node -v; python3 -V
```

A Web export **cannot** use Forward+/Mobile renderers. Set `gl_compatibility` in
`project.godot` and expect no SSAO/SDFGI/SSR: build the look from emissive materials, depth
fog, a dim directional moon and point lights instead.

## Stage 1 - Blender assets

Read `reference/blender-assets.md` for the helper library and the full checklist.
Load `templates/blender/common.py` as the starting point; it provides `box/sphere/cyl`,
material builders, armature construction, **part-scoped skinning**, pose/keyframe helpers
and viewer publishing.

Coordinate contract (get this wrong and everything is sideways):

| Blender | Godot | meaning |
|---|---|---|
| `+Y` | `-Z` | model forward |
| `+Z` | `+Y` | up |
| origin | origin | feet / ground contact |

Two structural traps that cost the most time:
* **Geometry is baked in world space.** A Blender object at the origin with vertices at
  absolute coordinates exports as a node at the origin. Collision boxes, sockets and
  "where is this prop" logic must therefore use **mesh AABBs transformed by the node**, or
  give the piece its own transform (see the next point).
* **Anything the engine must rotate needs its own pivot**: wheels, leg segments, turrets,
  doors. Build the piece centred on its own origin, then set `obj.location` to the joint.

## Stage 2 - Godot runtime

Read `reference/godot-runtime.md`. Highlights:
* Keep `main.tscn` to a single node and build the world in GDScript; hand-written `.tscn`
  with many nodes is fragile and unverifiable.
* Bind input in code (`InputMap.add_action`) instead of serialising `InputEventKey` blobs.
* Cache-bust exports by exporting to a versioned basename (`play2.html` -> `play2.pck`);
  a long `max-age` on `.pck`/`.wasm` will pin players to a stale build.
* On web, drive look with raw `movementX/movementY` from a JS accumulator, drained each
  physics frame. Godot's own deltas are window-relative: without pointer lock the pointer
  sticks at the screen edge and the view can never pan 360.

## Stage 3 - verification harness

Copy the `_verify` pattern from `templates/godot/verify_pattern.gd` into the game root and
run `godot --path game -- --verify`. Keep the harness **flag-gated** so it ships harmless.

Make game state observable: a small always-on readout (position, heading, health, ammo,
distance to target) turns every screenshot into data and makes agent-driven testing possible.

## Stage 4 - export and host

```bash
godot --headless --path game --export-release "Web" "$PWD/build/web/index.html"
python3 tools/serve.py build/web 8123          # gzip + mtime-aware, binds 0.0.0.0
```
For a public URL see `reference/hosting-and-verification.md`: pin the SSH forward to
`127.0.0.1` (`localhost` resolves to `::1` first and the tunnel returns 503), supervise the
tunnel in a restart loop, and write the current URL to `PUBLIC_URL.txt` because free
tunnels rotate their hostname on every reconnect.

## Stage 5 - live verification and fixes

* The agent browser tool usually **refuses loopback** - verify through the public tunnel.
* After each change: reload, screenshot, and read the on-screen readout to confirm the
  change took effect. Never claim a visual fix without a fresh frame.
* Keep a log of what each screenshot proved; the operator is watching live.

## Deliverable checklist

- [ ] assets rebuild from scripts, published to the viewer
- [ ] self-test prints numeric evidence for the new feature
- [ ] web export rebuilt (stable + versioned entry) and served with gzip
- [ ] public URL verified HTTP 200 and given to the operator
- [ ] `SPEC.md` updated: what changed, what was verified, what is still open
