# 3D Web Game Pipeline (Blender → Unity or Godot → Browser)

Use this skill when asked to build, extend, debug or host a real 3D game that runs in a
browser, especially when Blender and/or Unity are the requested tools, and when the work must
be *verified running*, not just written.

## Non-negotiable rules

1. **Asset geometry is generated by scripts, never by hand.** Every asset family gets its own
   headless Blender script so it is deterministic, re-runnable and diffable. One asset family,
   one script, one `.glb` (viewer/Godot) and one `.fbx` (Unity).
2. **Publish every build to the panel.** Models (`.glb`) and renders (`.png`) land in the 3D
   viewer after *every* build. While a game engine is being driven, the engine's own live view
   belongs in the sidebar too (`dsh-plugin-unity-live` for Unity, the Live Browser panel for the
   served build) — the operator must be able to watch without asking.
3. **Verify with numbers, not vibes.** A single self-test that drives the real systems and
   asserts distances, health deltas, ammo and hit rates. A feature is only "done" when the
   self-test prints evidence.
4. **Never leave a broken server.** Build exports into a staging dir, then swap; keep the host
   process alive; tell the operator the exact URL.
5. **Two-failure pivot.** If the same approach fails twice, stop and change technique (the
   "trap" entries in `reference/` exist precisely because most first approaches fail).

## Stage -1 - pick the engine before anything else

| | Unity 6 LTS | Godot 4 |
|---|---|---|
| Browser build | WebGL via IL2CPP; 40–80 MB; URP post stack, real materials, shadows | Web/WASM; ~40 MB; Compatibility renderer only — no SSAO/SDFGI/SSR |
| Asset import | FBX through the native importer, materials remapped at runtime | glTF, materials arrive intact |
| Best when | the brief says Unity, or wants a realistic lit look (URP + HDR + bloom + PBR maps) | the brief wants fast iteration and a small download |
| Live view | `dsh-plugin-unity-live` sidebar panel (game + scene views) | Streamed via the Live Browser panel once served |

Both paths share stages 1 (Blender assets), the hosting stage and the verification discipline.
Unity-specific work is `reference/unity-runtime.md`; Godot-specific work is
`reference/godot-runtime.md`.

**Unity prerequisites are heavier and fail loudly.** Confirm, in this order, before writing any
game code: the `unity` CLI exists → `unity auth status` is `loggedIn: true` →
`unity license status` is `"active": true` → an Editor with the WebGL module is installed. A
bare `unity license activate` exits 0 and activates nothing; see the reference for the form that
works.

## Stage 0 - recon

```bash
blender --version                        # 4.x, for the asset scripts
unity --version; godot --version         # whichever engine the brief names
unity editors --installed --format json
node -v; python3 -V
```

## Stage 1 - Blender assets

Read `reference/blender-assets.md`. Load `templates/blender/common.py` as the starting point:
`box/sphere/cyl`, material builders, armature construction, **part-scoped skinning**,
box-projected UVs, pose/keyframe helpers, FBX + GLB export, viewer publishing.

Contract, which differs per engine — get it wrong and everything is sideways:

| Blender | Unity | Godot | meaning |
|---|---|---|---|
| `+Y` | `-Z` | `-Z` | model forward |
| `+Z` | `+Y` | `+Y` | up |
| origin | origin | origin | feet / ground contact |

Both engines therefore need the imported instance rotated 180° about Y so the model faces the
engine's `+Z`; do it in one helper (`Warp.ApplyBlenderConvention` in the Unity templates) rather
than per asset.

Two structural traps that cost the most time:
* **Geometry is baked in world space.** A Blender object at the origin with vertices at absolute
  coordinates exports as a node at the origin. Collision boxes, sockets and "where is this prop"
  logic must use **mesh bounds transformed by the node** — and in Unity that means
  `InverseTransformVector`, not `size / lossyScale` (see the reference: the rotation permutes the
  extents and a ground slab becomes a wall).
* **Anything the engine must rotate needs its own pivot**: wheels, leg segments, turrets, doors.
  Build the piece centred on its own origin, then set `obj.location` to the joint.

## Stage 2 - engine runtime

**Unity**: read `reference/unity-runtime.md`. Highlights: `globalScale = 0.01f` on FBX import or
everything is 100× too large; `activeInputHandler: 2` or legacy `Input` throws; build the scene in
code from a `[RuntimeInitializeOnLoadMethod]` boot so no `.unity` file is hand-maintained;
generate the AnimatorController from the FBX clips and drive it with `CrossFadeInFixedTime`;
add runtime `Shader.Find` shaders to Always Included Shaders; start the Editor with
`unity open <project> --args "-automated"` and never hand-edit scene YAML while it is running.

**Godot**: read `reference/godot-runtime.md`. Highlights: keep `main.tscn` to a single node and
build the world in GDScript; bind input in code; version the export basename to cache-bust; on
web drive look from raw `movementX/movementY` (Godot's deltas are window-relative, so the view
can never pan 360 without pointer lock).

## Stage 3 - verification harness

**Unity**: one `VerifyDriver` MonoBehaviour driving the real systems from a scripted-input
static, printing PASS/FAIL with numbers, parked in a static the agent reads back with a single
`unity_eval`. Start it, wait, read `LastReport`. Details and calibration numbers in the reference.

**Godot**: copy the `_verify` pattern from `templates/godot/verify_pattern.gd` and run
`godot --path game -- --verify`; keep it flag-gated so it ships harmless.

Either way, make game state observable: an always-on readout (position, heading, health, ammo,
distance to target) turns every screenshot into data and makes agent-driven testing possible.

## Stage 4 - export and host

```bash
# Unity
unity build "$PROJECT" --target WebGL \
  --execute-method Neon.EditorTools.BuildScript.WebGL --allow-install --non-interactive --format json
python3 tools/serve.py build/unity 8124

# Godot
godot --headless --path game --export-release "Web" "$PWD/build/web/index.html"
python3 tools/serve.py build/web 8123
```

`templates/serve.py` is gzip- and MIME-complete for both engines. For a public URL see
`reference/hosting-and-verification.md`: pin the SSH forward to `127.0.0.1` (`localhost` resolves
to `::1` first and the tunnel returns 503), supervise the tunnel in a restart loop, and write the
current URL to `PUBLIC_URL.txt` because free tunnels rotate their hostname on every reconnect.

## Stage 5 - live verification and fixes

* **Put the engine in the sidebar.** `dsh-plugin-unity-live` streams the Unity Editor's game and
  scene views into the workbench panel; the Live Browser panel shows the served build. Do not
  make the operator alt-tab to follow progress.
* The agent browser tool usually **refuses loopback** — verify through the public tunnel, or
  capture from inside the engine.
* After each change: capture, read the on-screen readout, and only then claim the fix. Never
  claim a visual fix without a fresh frame.
* Long builds (engine install, first import, WebGL player build) run detached with a log; poll,
  and keep working on assets meanwhile.

## Deliverable checklist

- [ ] assets rebuild from scripts (`.glb` for the viewer, `.fbx` for Unity) and publish to the panel
- [ ] the engine's live view is reachable in the DSH sidebar, not just on the operator's desktop
- [ ] self-test prints numeric evidence for the new feature
- [ ] web export rebuilt (staging + swap) and served with gzip
- [ ] public URL verified HTTP 200 and given to the operator
- [ ] `SPEC*.md` updated: what changed, what was verified, what is still open
